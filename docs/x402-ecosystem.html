x402 — the ecosystem, end to end

How a machine pays for a single HTTP request with no account, no invoice and no identity — who the participants are, what the Bazaar adds on top, and where our own pieces sit on the rail.

Prepared 2026-08-05 · rewritten for x402 v2 2026-09-25 Protocol facts from x402-foundation/x402 specs/x402-specification-v2.md and its HTTP transport and exact scheme documents Discovery facts from docs.cdp.coinbase.com/x402 Obolus project documentation

This page describes x402 v2, the only version Obolus speaks. Where this page and the v2 specification disagree, the specification wins.

the rail — protocol surface, challenge and payload settlement — facilitator, chain, funds discovery — the Bazaar catalog

The short version

  • x402 revives HTTP 402. A server answers an unpaid request with 402 and a machine-readable list of ways to pay in a PAYMENT-REQUIRED header; the client picks one, signs it, and retries with the payment in a PAYMENT-SIGNATURE header. No account is created, so nothing identifies the buyer.
  • The seller never touches a chain. A facilitator verifies the signed authorization and broadcasts settlement. That is what lets a gateway hold no keys and still take money.
  • The Bazaar is the index. Discovery turns "you must already know the URL" into a browsable, searchable catalog of payable resources — the same accepts data, published ahead of the request instead of only in the 402.
  • Obolus is a seller on this rail. It fronts local inference and charges per request — so the buyers it serves are agent harnesses and apps that need a resource for a fee, without either side holding an account with the other.
01

The cast

Five roles. Any one participant can hold more than one — a gateway that also lists itself in the catalog is playing seller and listing at once — but the roles stay distinct because they trust each other differently.

Buyer

Client

Makes the request, receives the challenge, chooses among the offered options, signs a payment authorization and retries. Holds a wallet and therefore holds the only key that matters.

02

The pay-per-request flow

This is the whole protocol. Everything else in this document is either a detail of one of these steps or a way of finding out that step 1 is worth making at all.

The client asks, and is refused

An ordinary request with nothing attached. The server answers 402 Payment Required with a PAYMENT-REQUIRED header: a base64-encoded PaymentRequired object naming the resource once and listing, in accepts, every payment option the server will honour — each complete enough to act on without a follow-up call. A v2 client reads the header, not the body. The transport leaves the body to the server — the spec's own example sends {}, and Obolus repeats the same JSON there for humans with curl. Decoded:

402 Payment Required PAYMENT-REQUIRED: <base64 of the object below> Cache-Control: no-store { "x402Version": 2, "resource": { "url": "https://obolus.example/v1/chat/completions", "description": "One chat completion", "mimeType": "application/json" }, "accepts": [ { "scheme": "exact", "network": "eip155:84532", ← CAIP-2: Base Sepolia "amount": "1000", ← atomic units. NOT 0.001 "asset": "0xUSDC_CONTRACT", "payTo": "0xSELLER_ADDRESS", "maxTimeoutSeconds": 60, "extra": { "name": "USDC", "version": "2" } ← the token's EIP-712 domain }, { "scheme": "exact", "network": "solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1", ← Solana Devnet "amount": "1000", ← same price, different rail "asset": "USDC_MINT_ADDRESS", "payTo": "SELLER_PUBKEY", "maxTimeoutSeconds": 60, "extra": { "feePayer": "SPONSOR_PUBKEY" } ← who co-signs and pays the fee } ] }

Addresses above are placeholders. Two entries, one resource: a wallet funded on Base takes the first, a Solana wallet takes the second, and the seller settles against whichever was actually used. extra is scheme-specific: an EVM exact client signs under the token's name and version, and a Solana exact client builds a transaction the named fee payer finishes signing.

402 + accepts[]

The client picks an option and signs

Options differ by chain, asset and price, so the choice is the client's — a wallet funded on Base cannot pay a Solana option. Under the exact scheme the client signs a payment of the quoted amount, but does not broadcast it: the facilitator does that later, at settle.

EVM EIP-3009 TransferWithAuthorization, signed EIP-712 from · to · value · validAfter · validBefore · nonce value must equal the requirement's amount exactly the reference client: validBefore = now + maxTimeoutSeconds SVM SPL TransferChecked, partially signed; the fee payer adds the last signature a transfer of at least the requirement's amount (overpayment is tolerated) the transaction expires with its recent blockhash, after roughly 60–90 s

EIP-3009 is the default of three EVM transfer methods, chosen per option with extra.assetTransferMethod: Permit2 covers tokens without EIP-3009, and ERC-7710 covers smart accounts that delegate. Obolus runs only the default.

Both lines matter for timing. The authorization carries its own expiry — on EVM, whatever the client chose for validBefore; on Solana, the blockhash lifetime — and everything that follows, verify, the work and settle, has to fit inside it.

retry, payment attached

The same request, carrying payment

The signed payload rides in a request header. It carries a copy of the option the client chose, so the server can tell which offer is being paid and refuse it if that offer has changed since. The copy is not quite verbatim: on Solana the client fills in fields such as the recent blockhash itself, and servers leave those out of the match. Note what has not happened: nothing has hit a chain, no funds have moved, and the server still has not served anything.

PAYMENT-SIGNATURE: <base64 PaymentPayload> { "x402Version": 2, "accepted": { …the chosen entry of accepts… }, "payload": { "signature": "0x…", "authorization": { from, to, value, validAfter, validBefore, nonce } } } on Solana, "payload" is { "transaction": "<base64, partially signed>" }
seller → facilitator

Verify before serving

The seller posts the payload to the facilitator's /verify, which checks the signature, the balance, the amount, the validity window and that the parameters match what was demanded — without broadcasting anything. A failure here costs nobody anything.

verified

Serve the work

Only now does the request reach the thing behind the gate — an inference call, an API response, whatever was being sold.

seller → facilitator

Settle, and hand back a receipt

/settle broadcasts the authorization and money moves. The response carries a settlement receipt back to the client, so the payer learns what it actually paid — and can look the transaction up — without watching the chain itself. If settlement fails, the client gets a 402 instead of the work.

PAYMENT-RESPONSE: <base64 SettlementResponse> { "success": true, "transaction": "0x…", "network": "eip155:84532", "payer": "0x…" }

Why the ordering is the interesting part

Verify precedes work; settle follows it. A client that cannot pay is turned away before any compute is spent, and a seller that cannot deliver has not yet taken the money. The expensive, irreversible step sits between two cheap reversible ones.

The same shape is what makes the anonymous path viable at all: because authorization is proved per request, the seller never needs an account to attach it to.

v2 names this ordering the authorization payment flow, and it is the default. The spec defines two others, selected per option with extra.paymentFlow: upfront (settle, then serve) and escrow (settle a deposit, serve, then settle the final charge). upfront is required on rails with no way to pull a payment after the fact, and the Solana exact scheme recommends it for long-running handlers; escrow is for a final charge that can differ from the deposit. Either way, the payer is committed before the work runs. When both are offered, the spec says clients should prefer authorization. Obolus runs authorization only.

Implementation trap

The work has to finish inside the payment window

Under authorization, settle comes after the work, but the payment expires on its own clock: on EVM, the reference client sets it maxTimeoutSeconds after signing, and the reference facilitator refuses to settle an authorization that is about to expire; on Solana, the signed transaction dies with its blockhash, whatever maxTimeoutSeconds says. A handler that runs past the window has done the work and cannot be paid for it: the client gets a 402, and a client that simply pays again can loop.

The specification defines the window as the maximum time allowed for payment completion, and the EVM scheme has the facilitator check that the authorization's validity window meets the requirements. Neither says what a seller should do when its work outlasts the window; the Solana exact scheme recommends upfront for long-running handlers. The TypeScript reference server defaults the window to 300 seconds. Obolus's handling of this is #83.

03

What is in the challenge

The challenge has two parts: resource, which says once what is being sold, and accepts, whose every entry is one complete offer. A client should be able to evaluate and pay an entry without asking anything further — which is why price, chain, asset and destination all travel together.

FieldRequiredWhat it carries
x402VersionrequiredThe protocol version: 2.
erroroptionalWhy payment is required this time — for example, that the last payment was refused.
resource.urlrequiredThe URL being paid for.
resource.descriptionoptionalHuman-readable statement of what is being sold.
resource.mimeTypeoptionalResponse content type.
resource.serviceName · tags · iconUrloptionalPresentation and filtering hints, the same ones a discovery listing uses.
accepts[].schemerequiredHow payment is constructed — exact is the one in general use.
accepts[].networkrequiredWhich chain, in CAIP-2 form (e.g. eip155:84532 for Base Sepolia). v1's short names such as base-sepolia are gone.
accepts[].amountrequiredThe price, in atomic token units — never a decimal. v1 called it maxAmountRequired.
accepts[].assetrequiredThe token: a contract address on EVM, a mint address on Solana. Normally USDC. The spec also allows an ISO 4217 code for fiat.
accepts[].payTorequiredWhere the money lands: the seller's address. The spec also allows a role constant such as "merchant".
accepts[].maxTimeoutSecondsrequiredThe maximum time allowed for payment completion. The reference EVM client also makes it the lifetime of the authorization it signs; a Solana payment expires with its blockhash instead. Obolus keeps the last 15 s of each window for settling, and refuses to start with a window of 15 s or less.
accepts[].extraoptionalScheme-specific additions — the EIP-712 token domain on EVM, the fee payer on Solana — plus two reserved keys, assetTransferMethod and paymentFlow, that pick how funds move and when settlement runs.
extensionsoptionalOptional protocol extensions. The client echoes what the server advertised.

An array, not a price

A seller advertising several entries is offering genuine alternatives — Base or Solana, one asset or another — and the client settles against exactly the option it chose. That is what stops multi-chain support from becoming a deployment decision the operator has to make in advance on the buyer's behalf.

04

The Bazaar — discovery on top of the rail

The base protocol assumes you already know the URL. That is fine for a client wired to one provider and useless for an agent that should be able to find a cheaper one. Discovery closes that gap by publishing the offer before anyone makes a request.

A seller opts in

Services using the CDP facilitator with the bazaar extension enabled are listed automatically. Listing is free, and sellers keep setting their own prices — the catalog indexes offers, it does not make them.

indexed

A buyer browses or searches

A paginated catalog endpoint returns resources with their payment options attached, filterable and searchable — hybrid full-text plus semantic retrieval, so an agent can ask for a capability rather than a hostname.

spec §8.1 GET /discovery/resources?limit=&offset= → { x402Version, items[], pagination } CDP GET /v2/x402/discovery/resources?limit=&offset= → { resources[], partialResults, searchMethod, x402Version }

The two shapes differ. Code written against one will not parse the other. The field table below is CDP's; several of its fields are not in the spec's discovery item.

…and then it is just section 02 again

Discovery hands back a URL and its price. From there the ordinary 402 handshake runs unchanged. Nothing about the payment path is special because the resource was found rather than known.

Implementation trap

The discovery entry is an advertisement, not the offer

In v2 the offers inside accepts share their field names — both price in amount, which under v1 the challenge called maxAmountRequired. The envelopes around them still differ: a challenge's resource is an object with a url, a discovery item's resource is the URL string itself. Code that assumes one shape silently mis-reads the other. A listing also names the x402Version it speaks, so check that before reading its fields.

Shared names do not make them the same thing. Treat the catalog entry as an advertisement of an offer and the 402 challenge as the offer itself. When they disagree, the challenge is authoritative: it is the one the seller will actually settle against, and a v2 payment names the exact challenge entry it accepted.

What discovery changes strategically

Once prices are published ahead of the request, an agent with a budget can comparison-shop, and a seller's price becomes visible next to others'. That is a market forming on top of a payment protocol — and it is the mechanism that makes agent-run budgets meaningful rather than decorative, because an agent can now choose to spend less instead of merely refusing to spend more.

Buyers and sellers never share a key, an account, or an identity — only a protocol and a facilitator they both trust to be honest about the chain.

Why a seller is also the best test rig

A gateway you operate is the most controllable counterparty a payment client can be exercised against: you decide what it charges, which chains it offers, and exactly how it behaves when payment is absent, malformed, expired, or refused mid-flight. Public providers will not fail on command.

So Obolus is useful to any x402 buyer twice over — as a real thing to pay for real inference, and as the fixture that makes the unhappy paths reproducible. That second role is the one that is hard to get anywhere else.

06

The pricing seam

x402's exact scheme prices a request, in atomic units, at the moment of asking. The model world prices tokens, in fractions of a cent, in published tables. A gateway selling inference over x402 stands exactly on that seam and has to reconcile the two.

 x402Model-metadata world
UnitOne requestPer input / output token
DenominationAtomic token units of a specific assetFiat fractions, provider-published
Where it livesaccepts[] — challenge or catalog entryA models endpoint or a pricing registry
Known when?Under exact, before the work — it is the offer. Under upto, a ceiling before and the actual charge afterAfter the work — it depends on token count

The reconciliation is a product decision, not a formatting one

Under exact, the price is fixed before the response length is known, so a seller either charges a flat rate per resource, estimates from the input and eats the variance, or splits the resource so each price band is its own URL. Discovery pushes toward the last of these: catalog entries are keyed on a resource, so per-model pricing means per-model resources.

v2 also offers a way out of that bind. The upto scheme has the client authorize a maximum, and the server settles the amount the work actually cost — for inference, the tokens generated. Obolus runs exact only today, and refuses to advertise any other scheme.

Where the protocol is silent — capability flags, context windows, per-token rates — the sensible move is to follow whoever the ecosystem already follows rather than coin new names: a live models endpoint shaped as an OpenAI superset, and cost/capability field vocabulary borrowed from the widely-mirrored pricing registries. Both are additive, so an OpenAI-shaped client keeps working and simply ignores what it does not understand.

07

Where our own pieces actually stand

Stated plainly, because a living document that flatters the implementation is worse than no document.

Live

Obolus speaks x402 v2: real 402 challenges in PAYMENT-REQUIRED, a multi-option accepts array, payments matched against the whole option they name, and receipts in PAYMENT-RESPONSE.

Proven once

A real payment round trip on Base Sepolia on 2026-09-24: the reference @x402/fetch client paid, x402.org settled, and the transaction matches the receipt and the gateway's telemetry (#72). Run by hand, outside the merge gate.

Live

An arming guard refuses to advertise any network not provably testnet unless explicitly armed — the challenge is the real-money trigger, so it is the thing that is guarded.

Live

A bearer-token path exists alongside the 402 branch, fail-closed: anything not positively verified takes the payment branch.

Worked around

No outbound TLS client, so the facilitator URL must be http://. A real facilitator is https://, so reaching one takes a TLS-terminating proxy in front of it, as the round trip did (#35).

Bounded

The trap in section 02: a paid request's upstream must answer within the payment window, less 15 s kept for settling. If it does not, the request fails uncharged with a 504 rather than being served and left unpaid. The window defaults to 300 s (#83). Giving up closes the connection to the model, and Ollama stops generating when that happens: seen on Ollama 0.34.4's MLX runner for streaming and non-streaming requests alike (#31).

Not yet proven

Solana options can be advertised, but no Solana payment has settled. A reference client needs extra.feePayer in the option, which Obolus neither fills in nor requires yet, so the operator has to supply it (#81).

By design

An unconfigured gateway is unpayable: placeholder network, no pay-to wallet. Inert by construction rather than by configuration.

Not yet

No discovery listing and no catalog presence. Prices can already differ by backend; per-model rates are later work.

What the round trip settled

The protocol claims are no longer only claims

Verification and settlement are the only steps that leave the building, and a fake we wrote proves nothing about a rail we do not control. The round trip against x402.org is the first evidence from outside our own authorship: a third-party facilitator accepted the challenge as we advertise it, the signature a reference client made under it, and the payment it settled.

It is one run by hand, not a check. Making it repeatable — outside the merge gate, so that its flakiness cannot block a merge — is still to do.
