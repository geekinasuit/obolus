x402 — the ecosystem, end to end

How a machine pays for a single HTTP request with no account, no invoice and no identity — who the participants are, what the Bazaar adds on top, and where our own pieces sit on the rail.

Prepared 2026-08-05 Protocol facts from coinbase/x402 specs/x402-specification-v1.md Discovery facts from docs.cdp.coinbase.com/x402 Obolus project documentation
the rail — protocol surface, challenge and payload settlement — facilitator, chain, funds discovery — the Bazaar catalog

The short version

  • x402 revives HTTP 402. A server answers an unpaid request with 402 and a machine-readable list of ways to pay; the client picks one, signs it, and retries with the payment attached. No account is created, so nothing identifies the buyer.
  • The seller never touches a chain. A facilitator verifies the signed authorization and broadcasts settlement. That is what lets a gateway hold no keys and still take money.
  • The Bazaar is the index. Discovery turns "you must already know the URL" into a browsable, searchable catalog of payable resources — the same accepts data, published ahead of the request instead of only in the 402.
  • Obolus is a seller on this rail. It fronts local inference and charges per request — so the buyers it serves are agent harnesses and apps that need a resource for a fee, without either side holding an account with the other.
01

The cast

Five roles. Any one participant can hold more than one — a gateway that also lists itself in the catalog is playing seller and listing at once — but the roles stay distinct because they trust each other differently.

02

The pay-per-request flow

This is the whole protocol. Everything else in this document is either a detail of one of these steps or a way of finding out that step 1 is worth making at all.

The client asks, and is refused

An ordinary request with nothing attached. The server answers 402 Payment Required with a body containing an accepts array — every payment option it will honour, each one complete enough to act on without a follow-up call.

402 Payment Required { "x402Version": 1, "accepts": [ { "scheme": "exact", "network": "base-sepolia", "maxAmountRequired": "1000", ← atomic units. NOT 0.001 "asset": "0xUSDC_CONTRACT", "payTo": "0xSELLER_ADDRESS", "resource": "https://obolus.example/v1/chat/completions", "description": "One chat completion", "mimeType": "application/json", "maxTimeoutSeconds": 60 }, { "scheme": "exact", "network": "solana-devnet", ← same price, different rail "maxAmountRequired": "1000", "asset": "USDC_MINT_ADDRESS", "payTo": "SELLER_PUBKEY", "resource": "https://obolus.example/v1/chat/completions", "description": "One chat completion", "mimeType": "application/json", "maxTimeoutSeconds": 60 } ] }

Addresses above are placeholders. Two entries, one resource: a wallet funded on Base takes the first, a Solana wallet takes the second, and the seller settles against whichever was actually used.

402 + accepts[]

The client picks an option and signs

Options differ by chain, asset and price, so the choice is the client's — a wallet funded on Base cannot pay a Solana option. Under the exact scheme the client signs an authorization to move a precise amount, rather than sending a transaction itself.

EVM EIP-3009 TransferWithAuthorization, signed EIP-712 from · to · value · validAfter · validBefore · nonce SVM SPL TransferChecked, fixed instruction layout amount must equal maxAmountRequired exactly
retry, payment attached

The same request, carrying payment

The signed payload rides in a request header. Note what has not happened: nothing has hit a chain, no funds have moved, and the server still has not served anything.

X-PAYMENT: <base64 payment envelope>
seller → facilitator

Verify before serving

The seller posts the payload to the facilitator's /verify, which checks the signature, the balance, the amount, the validity window and that the parameters match what was demanded — without broadcasting anything. A failure here costs nobody anything.

verified

Serve the work

Only now does the request reach the thing behind the gate — an inference call, an API response, whatever was being sold.

seller → facilitator

Settle, and hand back a receipt

/settle broadcasts the authorization and money moves. The response carries a settlement receipt back to the client, so the payer learns what it actually paid without watching the chain itself.

X-PAYMENT-RESPONSE: <base64 settlement receipt>

Why the ordering is the interesting part

Verify precedes work; settle follows it. A client that cannot pay is turned away before any compute is spent, and a seller that cannot deliver has not yet taken the money. The expensive, irreversible step sits between two cheap reversible ones.

The same shape is what makes the anonymous path viable at all: because authorization is proved per request, the seller never needs an account to attach it to.

03

What is in the challenge

Each entry of accepts is one complete offer. A client should be able to evaluate and pay it without asking anything further — which is why price, chain, asset and destination all travel together.

FieldRequiredWhat it carries
schemerequiredHow payment is constructed — exact is the one in general use.
networkrequiredWhich chain, in CAIP-2 form (e.g. base-sepolia).
maxAmountRequiredrequiredThe price, in atomic token units — never a decimal.
assetrequiredToken contract address. Normally USDC.
payTorequiredWhere the money lands. The seller's address.
resourcerequiredThe URL being paid for.
descriptionrequiredHuman-readable statement of what is being sold.
maxTimeoutSecondsrequiredHow long the offer stays payable. A zero window is unpayable.
mimeTypeoptionalResponse content type.
outputSchemaoptionalJSON schema of the response — what a buyer gets for the money.
extraoptionalScheme-specific additions.

An array, not a price

A seller advertising several entries is offering genuine alternatives — Base or Solana, one asset or another — and the client settles against exactly the option it chose. That is what stops multi-chain support from becoming a deployment decision the operator has to make in advance on the buyer's behalf.

04

The Bazaar — discovery on top of the rail

The base protocol assumes you already know the URL. That is fine for a client wired to one provider and useless for an agent that should be able to find a cheaper one. Discovery closes that gap by publishing the offer before anyone makes a request.

A seller opts in

Services using the CDP facilitator with the bazaar extension enabled are listed automatically. Listing is free, and sellers keep setting their own prices — the catalog indexes offers, it does not make them.

indexed

A buyer browses or searches

A paginated catalog endpoint returns resources with their payment options attached, filterable and searchable — hybrid full-text plus semantic retrieval, so an agent can ask for a capability rather than a hostname.

GET /v2/x402/discovery/resources?limit=&offset= → { resources[], partialResults, searchMethod, x402Version }
resource + accepts[]

…and then it is just section 02 again

Discovery hands back a URL and its price. From there the ordinary 402 handshake runs unchanged. Nothing about the payment path is special because the resource was found rather than known.

Implementation trap

The discovery entry is not byte-identical to the challenge

The 402 challenge names the price maxAmountRequired; the discovery entry names it amount. They describe the same thing, and code that assumes one shape will silently mis-read the other — a price field that parses to nothing is the worst possible field to get wrong.

Treat the catalog entry as an advertisement of an offer and the 402 body as the offer itself. When they disagree, the challenge is authoritative: it is the one the seller will actually settle against.

What discovery changes strategically

Once prices are published ahead of the request, an agent with a budget can comparison-shop, and a seller's price becomes visible next to its rivals'. That is a market forming on top of a payment protocol — and it is the mechanism that makes agent-run budgets meaningful rather than decorative, because an agent can now choose to spend less instead of merely refusing to spend more.

Buyers and sellers never share a key, an account, or an identity — only a protocol and a facilitator they both trust to be honest about the chain.

Why a seller is also the best test rig

A gateway you operate is the most controllable counterparty a payment client can be exercised against: you decide what it charges, which chains it offers, and exactly how it behaves when payment is absent, malformed, expired, or refused mid-flight. Public providers will not fail on command.

So Obolus is useful to any x402 buyer twice over — as a real thing to pay for real inference, and as the fixture that makes the unhappy paths reproducible. That second role is the one that is hard to get anywhere else.

06

The pricing seam

x402 prices a request, in atomic units, at the moment of asking. The model world prices tokens, in fractions of a cent, in published tables. A gateway selling inference over x402 stands exactly on that seam and has to reconcile the two.

 x402Model-metadata world
UnitOne requestPer input / output token
DenominationAtomic token units of a specific assetFiat fractions, provider-published
Where it livesaccepts[] — challenge or catalog entryA models endpoint or a pricing registry
Known when?Before the work — it is the offerAfter the work — it depends on token count

The reconciliation is a product decision, not a formatting one

A per-request price must be fixed before the response length is known, so a seller either charges a flat rate per resource, estimates from the input and eats the variance, or splits the resource so each price band is its own URL. Discovery pushes toward the last of these: catalog entries are keyed on a resource, so per-model pricing means per-model resources.

Where the protocol is silent — capability flags, context windows, per-token rates — the sensible move is to follow whoever the ecosystem already follows rather than coin new names: a live models endpoint shaped as an OpenAI superset, and cost/capability field vocabulary borrowed from the widely-mirrored pricing registries. Both are additive, so an OpenAI-shaped client keeps working and simply ignores what it does not understand.

07

Where our own pieces actually stand

Stated plainly, because a living document that flatters the implementation is worse than no document.

Live

Obolus issues real 402 challenges and advertises a multi-option accepts array. Deployed loopback-only.

Live

An arming guard refuses to advertise any network not provably testnet unless explicitly armed — the challenge is the real-money trigger, so it is the thing that is guarded.

Live

A bearer-token path exists alongside the 402 branch, fail-closed: anything not positively verified takes the payment branch.

Blocked

No outbound TLS client, so the facilitator URL must be http://. A real facilitator is https:// — settlement therefore cannot run yet.

Not yet

The deployed instance is deliberately unpayable: placeholder network, no pay-to wallet. Inert by construction rather than by configuration.

Not yet

No discovery listing, no catalog presence, and no per-model resource split.

The one that gates the rest

Everything downstream waits on reaching a real facilitator

Verification and settlement are the only steps that leave the building, and they are the steps we cannot yet take. Until an https:// facilitator is reachable — by wiring a TLS client or by terminating TLS in front of the gateway — the 402 path is exercisable only against fakes, and a fake we wrote proves nothing about a rail we do not control.

That is also why a payable testnet instance is the milestone worth aiming at rather than a broader feature set: it is the first point at which the protocol claims stop being claims.
